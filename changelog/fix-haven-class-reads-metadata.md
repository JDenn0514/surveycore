# Changelog: fix/haven-class-reads-metadata

**Branch:** `fix/haven-class-reads-metadata`
**Status:** Complete
**Date:** 2026-09-02

## Summary

Fixes #205: `survey_data(x, haven_class = TRUE)` rebuilt the labelled class
from the column's `labels` attribute and from nothing else. A design's
`set_val_labels()` writes `@metadata@value_labels` and touches no column
(`R/core-metadata.R:2547`), so the two stores disagree the moment an analyst
corrects a label. The rebuild read the store the setter does not write, and it
did so silently.

That defeats the one job §VIII.1 of the archived spec gives the argument: stop
an analyst exporting a design to `.sav` and losing the value labels without
being told. In the ordinary workflow — import a `.sav`, correct the labels with
`set_val_labels()`, export — it wrote the wrong labels instead of none.

Two failures, both from the issue, measured before the fix:

```r
# 1. Corrected labels come back stale.
d <- set_val_labels(d, q = c(Bad = 1, Ok = 2, Good = 3))
attr(survey_data(d, haven_class = TRUE)$q, "labels")
#>  Low  Mid High        # the labels the import set
#>    1    2    3

# 2. Labels created on the design never appear at all.
d <- set_val_labels(as_survey(df, ids = id, weights = wt), q = c(No = 1, Yes = 2))
class(survey_data(d, haven_class = TRUE)$q)
#> [1] "numeric"          # haven_class = TRUE gives what FALSE gives
```

`set_var_label()` failed the same way, for the same reason: it writes
`@metadata@variable_labels` and the rebuild read `attr(col, "label")`.

## The fix

`survey_data()` holds `x@metadata`, so it passes each column's two metadata
entries into `.restore_haven_class()`. The helper writes each entry it is given
onto the column, and the column's own attribute is the fallback for each. That
is the order `.extract_var_meta()` has always used
(`R/analysis-helpers.R:160-166`).

Value labels from either store are still the whole class test, so the
`sjlabelled` promotion issue #207 settled is unchanged — it now comes from the
fallback. Rows `X-18` to `X-20` pass untouched.

One limit stays, and it is a consequence of #207 rather than a new decision:
`set_val_labels(x, v = NULL)` clears the metadata entry and leaves the column's
attribute in place, so the fallback rebuilds the class from that attribute.
Telling a cleared entry from one that was never set needs the provenance state
#207 refused. Documented in `@param haven_class`, in the helper comment, and in
D5.

`haven_class = FALSE` is untouched. It returns `@data` unchanged, with no copy
and no attribute read, exactly as before.

## Changes

- Read the design's metadata before the column's own attributes when
  `haven_class = TRUE`, so value labels set by `set_val_labels()` and variable
  labels set by `set_var_label()` on a design reach the returned column
- Keep the column attribute as the fallback for each, so the `sjlabelled`
  promotion settled by #207 is unchanged
- Document the resolution order and the one remaining limit in
  `@param haven_class`, in the `@return` text, in the helper comment, and in D5
- Add four test rows covering the corrected-label case, the created-label case,
  the variable-label case, and a variable label on a column with no value labels
- Record dated corrections in the two archived haven-labelled planning
  documents, which named the attribute as the only store the rebuild reads

## Tests

Four new rows, all four failing before the fix and passing after:

| Row | Asserts |
|---|---|
| `X-21` | corrected labels come from the metadata, not the stale attribute |
| `X-22` | a column with no `labels` attribute at import is promoted from the metadata alone |
| `X-23` | `set_var_label()` on the design reaches the returned column's `label` |
| `X-24` | a metadata variable label reaches a column with no value labels, which still gets no class |

`X-21` also asserts the returned attribute equals `extract_val_labels(d, dbl)`,
so the rebuild and the extractor cannot drift apart again.
