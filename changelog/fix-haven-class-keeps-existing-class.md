# Changelog: fix/haven-class-keeps-existing-class

**Branch:** `fix/haven-class-keeps-existing-class`
**Status:** Complete
**Date:** 2026-09-03

## Summary

Fixes #206: `.restore_haven_class()` assigned the haven class chain whenever
the column had value labels, without ever reading what the column already
was. `attr(x, "class") <- ...` replaces the whole class vector, so a `factor`
that carried a `labels` attribute came back from
`survey_data(x, haven_class = TRUE)` as a `haven_labelled` vector of its level
codes, and a `Date` came back as its day count. The levels, and the dates,
were gone.

The route in needs no `haven`: `set_val_labels()` in data-frame mode writes
the attribute onto any column, whatever its type (`R/core-metadata.R:2549`).
Nothing warned at any step — the labels covered every observed level, so
`surveycore_warning_missing_labels` stayed quiet too.

Measured before the fix:

```r
df <- data.frame(id = 1:6, wt = rep(1, 6), f = factor(c("a", "b", "c", "a", "b", "c")))
df <- set_val_labels(df, f = c(a = "a", b = "b", c = "c"))   # no warning
d  <- as_survey(df, ids = id, weights = wt)

class(survey_data(d, haven_class = TRUE)$f)
#> [1] "haven_labelled" "vctrs_vctr"     "integer"
unclass(survey_data(d, haven_class = TRUE)$f)[1:3]
#> [1] 1 2 3                # the codes; the levels are gone
```

With `haven` absent the next call on that column raises a `vctrs` error, which
is the failure mode the whole `haven_labelled` series (#175) exists to remove.

No bundled dataset carries a factor with a `labels` attribute, so no test in
the suite hit this. It needs a user frame, or `set_val_labels()` on a data
frame.

## The fix

`.restore_haven_class()` returns early on `is.object(x)` — a column that
carries a class attribute of its own. A `factor` keeps its levels, a `Date`
keeps its calendar, and any other classed column comes back as it went in.
There is no haven class to rebuild on such a column, and `.strip_labelled_*()`
only ever removes `haven_labelled`, so a classed column reaching the helper
never carried one.

The guard sits after the two attribute writes, not before them, so the
`label` and `labels` attributes still follow the design's metadata on a
classed column. That matches row `X-24`, where an unclassed column that gets
no class still takes its metadata label. A variable label on a factor is what
`haven::write_sav()` writes as the variable's name, so dropping it would trade
one silent loss for another.

This narrows the promotion issue #207 settled; it does not reopen it. #207
refused a *provenance* record — new state saying which columns arrived
labelled. The class attribute is not that record: it is on the column, it
costs one `is.object()` call, and it says what the column is now rather than
where it came from.

`haven_class = FALSE` is untouched, and the unclassed rebuild is unchanged:
rows `X-18` to `X-24` pass with no edit.

## Changes

- Skip the class rebuild on a column that carries a class of its own, so a
  `factor`, a `Date`, and every other classed column survive
  `survey_data(haven_class = TRUE)` intact
- Keep the two attribute writes ahead of the guard, so a metadata variable
  label still reaches a factor column
- Document the case in `@param haven_class`, in the `@return` text, and in the
  helper comment
- Add three test rows and record dated corrections in the two archived
  haven-labelled planning documents
